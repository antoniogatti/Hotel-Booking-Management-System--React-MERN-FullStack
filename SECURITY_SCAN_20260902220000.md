**High-Priority Findings (Action now)**

H1 — Session token in URL + `localStorage` token model (High)
- Impact: tokens exposed in URL, browser history, referrers; `localStorage` tokens are accessible to any injected script (XSS).
- Evidence: OAuth callback and token persistence flow:
  - [hotel-booking-backend/src/routes/auth.ts](hotel-booking-backend/src/routes/auth.ts)
  - [hotel-booking-frontend/src/pages/AuthCallback.tsx](hotel-booking-frontend/src/pages/AuthCallback.tsx)
  - [hotel-booking-frontend/src/api-client.ts](hotel-booking-frontend/src/api-client.ts)
  - [hotel-booking-frontend/src/lib/api-client.ts](hotel-booking-frontend/src/lib/api-client.ts)
- Recommendation (remediation):
  1. Stop returning JWTs in query strings from OAuth callbacks. Remove `token` from redirect URLs.
  2. Issue server-set session cookie (`Set-Cookie`): `HttpOnly`, `Secure`, `SameSite=lax` (or `Strict` where applicable), short TTL.
  3. Remove client-side `localStorage` persistence of `session_id` and remove axios interceptor-based Bearer injection; rely on cookie auth + `GET /api/auth/validate-token` to bootstrap client state.
  4. Implement CSRF protection (double-submit cookie or CSRF token header) for state-changing endpoints if cookies are used for auth.
- Estimated effort: 1–3 developer days (backend + frontend + QA).
- Safe plan / rollback: implement behind a feature flag; deploy to staging, exercise sign-in and role flows; if regressions appear, revert the feature commit and rotate the JWT secret as a precaution.

H2 — Service auth endpoints mint long-lived admin JWTs with static shared secret (High)
- Impact: brute-force or credential leak could allow issuance of admin tokens (high blast radius).
- Evidence: [hotel-booking-backend/src/routes/mcp.ts](hotel-booking-backend/src/routes/mcp.ts) (12h tokens) and similar service auth code.
- Recommendation:
  1. Add strict rate limiting and an account lockout/backoff for service auth endpoints.
  2. Reduce service token TTL (15–60 minutes) and support short-lived refresh/rotation.
  3. Introduce audit logging for service auth calls and consider IP/source restrictions or mutual-TLS where appropriate.
  4. Prefer managed-identity, client-assertions, or short-lived credentials rather than a long-lived static secret.
- Estimated effort: 1–2 dev days.
- Safe plan / rollback: Change TTL and rate-limits behind config; monitor logs and allow rollback if integration clients fail. Rotate the secret if suspicion of leak.

H3 — Vulnerable dependencies backlog (High)
- Impact: transitive CVEs (SSRF, prototype pollution, DoS) increase runtime risk.
- Evidence: local `npm audit` summary and the repo dependency tree (high-risk libs include `axios`, `express`, `mongoose`, `react-router-dom`, `js-cookie`).
- Recommendation:
  1. Plan a controlled upgrade wave (FE first for `axios` and router stack, BE for `express`, `mongoose`).
  2. Add CI gating: `npm audit --audit-level=high` fail threshold for production branch.
  3. Run integration tests and smoke-tests in staging after each major upgrade.
- Estimated effort: 2–7 dev days (depends on major version bumps and test coverage).
- Safe plan / rollback: Migrate in small PRs, pin working versions, use semantic-release branches; rollback by reverting PRs.

H4 — Key Vault network ACLs and public access (High)
- Impact: Key Vault remains reachable publicly (network-level exposure); increases risk of secret-targeting attacks.
- Evidence: [infra/main.bicep](infra/main.bicep) (Key Vault `publicNetworkAccess: 'Enabled'` and `networkAcls.defaultAction: 'Allow'`).
- Recommendation:
  1. Move to `networkAcls.defaultAction = 'Deny'` and enable a private endpoint for the Key Vault.
  2. Where private endpoint adoption is not immediately possible, restrict allowed IPs until private endpoint is configured.
  3. Validate App Service identity/key rotation flows before enforcing deny-by-default.
- Estimated effort: 1–3 ops days (involve infra deploy windows and validation).
- Safe plan / rollback: Prepare rollback runbook to re-enable publicNetworkAccess if services fail to read secrets; test in pre-prod.

H5 — App Service publicNetworkAccess enabled (High)
- Impact: backend app is publicly accessible, increasing attack surface; should be intentionally hardened.
- Evidence: [infra/main.bicep](infra/main.bicep) (backendSite `publicNetworkAccess: 'Enabled'`).
- Recommendation:
  1. Front the app with a WAF (Azure Front Door or Application Gateway WAF) and restrict direct app access using Access Restrictions (IP/Service filters) and App Service authentication where needed.
  2. Consider enabling Private Endpoint + Front Door routing for production.
- Estimated effort: 2–5 ops/dev days.
- Safe plan / rollback: Staged rollout through staging fronted by WAF; revert access restriction changes if false positives prevent legitimate traffic.

**Actions Performed (Phase A) — executed 2026-09-03**

The following changes were implemented as part of Phase A remediation and hardening. All edits were made in-repo and are summarized with file references.
